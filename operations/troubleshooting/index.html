    Troubleshooting runbook

    One failure class at a time: unhealthy services, a login loop, a task that never forwards, a stuck queue, FloodWait, busy ports and truncated logs.

    This is the page you open when something is wrong. Every section names the symptom as you meet it, the cause in the implementation, the exact commands to run and the evidence that proves the fix. Nothing here asks you to guess.

    Fast triage

    Four commands, cheapest first, tell you whether the failure is the stack, the configuration or the rules. Run them before reading any single section below.

    atf validate --strictConfig, compose, catalog parity and a secrets scan; exits non-zero on warnings too.
    atf doctorDeep checks across docker, the containers and their network aliases, ports, the API, the services, the database, logs, sessions, certificates, disk and AI providers. Exit code 0 when nothing failed, 1 when any check failed.
    atf logs query --level ERRORAttributable error history — actor, service, subject task, correlation id.

    A service will not start, or is unhealthy

    Symptom. The dashboard is blank, forwarding stopped, or a service shows red on the board.Cause. One container is down — a crash loop, a missing env key, or a port already bound. The stack tolerates a down web or logger without stopping delivery, but a down core reads nothing from Telegram.

    Confirm the fix with atf system services (all four OK) andcurl -s localhost:8080/api/health/services | jq .status returning healthy. The port contract each service is probed on is fixed:

    Port contract

    web8088Rust Axum gateway plus the React SPA; also proxies /api.
    core50051Python engine over gRPC — reads Telegram and runs the pipeline.
    logger50052Log ingest and query service over gRPC.

    Fix the port owner, do not remap blindly

    If two services disagree about a port, remapping one hides the conflict and breaks the reverse proxy's upstream resolution. atf validate --runtime reports which process owns a busy port so you can stop the right thing.

    Dashboard login fails or loops

    Symptom. The link from the bot bounces back to the login screen, or the dashboard keeps asking you to re-authenticate. Cause. A dashboard link carries a single-use code, not a session token: codes live 600 seconds, are burned on first exchange, and only the core that minted one can trade it for a session. A second tab, a refresh or a link replayed from chat history all fail the same way.

    Login error codes
    ResponseMeaning
    401 LOGIN_CODE_REQUIREDNo login code was sent to POST /api/auth/exchange-bot-token.
    401 INVALID_LOGIN_CODEThe code is used, expired or unknown. Core answers the same for all three on purpose.
    429 COOLDOWNA still-valid link was minted for this user inside the 60-second cooldown. Retry-After carries the seconds left.

    • 401 LOGIN_CODE_REQUIRED

      Meaning
      No login code was sent to POST /api/auth/exchange-bot-token.

    • 401 INVALID_LOGIN_CODE

      Meaning
      The code is used, expired or unknown. Core answers the same for all three on purpose.

    • 429 COOLDOWN

      Meaning
      A still-valid link was minted for this user inside the 60-second cooldown. Retry-After carries the seconds left.

    The re-login hand-off is deliberate

    When the stored session is dead, the dashboard calls GET /api/auth/bot-login-link instead of looping. That endpoint mints for the caller's own verified identity only — never a user id from the body — and answers 429 COOLDOWN with a Retry-After header when a link from the last click is still live, rather than invalidating it.

    A task creates but never forwards

    Symptom. The rule saves and shows as active, but posts from the source never reach the target.Cause. Almost always one of five things: the bot is not an admin in the source or the target, the channel id is a username where a numeric id is required (or the reverse), the rule is paused, deduplication recognises the post, or a filter drops it.

    [PIPELINE:FILTER_DROP]A filter rejected the post. Expected only if the rule says so.
    [PIPELINE:CLEAN]The cleaner removed content, leaving nothing worth sending.
    [PIPELINE:RESTRICTED_BYPASS]Protected content was re-uploaded instead of forwarded. Normal copy-protection handling.
    [PIPELINE:DELIVERED]Telegram confirmed the delivery.

    The bot must be an admin in both chats

    A bot that is only a member cannot post. Telegram answers ChatAdminRequired, which ATF classifies as err_admin_required and surfaces as “check admin”. Add the bot as an administrator of the source and of each target, then re-run atf rules simulate.

    Numeric id versus @username

    Telegram resolves a numeric chat id and an @username differently, and a bot cannot always resolve a username it has never seen the chat through. When a target stays silent while the simulation matches, store the numeric id the bot reports and try again.

    Paused rules keep their queued work

    A paused rule never forwards new messages, and jobs already queued for it are deferred with backoff rather than dropped, so resuming continues exactly where it stopped. Check the rule state before assuming a bug.

    Deduplication and filters

    A SHA-256 content fingerprint suppresses a post the rule has already delivered, and any active filter — keyword, link rule, media type — drops it outright with a [PIPELINE:FILTER_DROP] line. The simulation reports the same decision without touching Telegram.

    Messages stuck in the queue or dead-lettered

    Symptom. Posts are accepted but nothing arrives, or the dashboard shows a growing backlog.Cause. A job is waiting in the durable queue or has exhausted its retries and landed in the dead-letter queue. Replay is deliberate: fix the cause first, then replay.

    FloodWait & protected posts

    Symptom. Deliveries stop for a while, then resume on their own; or a post arrives re-uploaded instead of as a forward. Cause. Telegram rate-limits accounts (FloodWait), and channels can forbid forwarding. Neither is a bug.

    1. The account is marked time-limited for the wait Telegram named, and its deliveries pause.
    2. Jobs stay queued in RETRY_WAIT; other accounts keep serving, so one limited account never stalls the installation.
    3. When a forward is refused because the channel is protected, the post is re-uploaded instead. Repeated FloodWaits mean your rates are too high, not that the code is broken.

    Do not fight a FloodWait

    Retrying immediately is how accounts get banned. Watch the wait in the logs and let the queue drain; if it happens constantly, lower the send rate rather than removing the backoff.

    “Port already in use”

    Symptom. A service fails to start with port already in use, often 8088or 8080. Cause. Another process — usually a previous stack that was not shut down — owns the port. The contract is fixed: api 8080, web 8088, core 50051, logger 50052.

    429 rate limiting

    Symptom. The dashboard or a script gets 429 Too Many Requests. Cause.The API enforces per-route limits in front of the control plane, and the unauthenticated auth endpoints are limited hardest. Every refusal names itself, so a client can pace itself instead of discovering the limit by being refused.

    Rate-limit responses
    StatusCodeReading it
    429rate_limitedBody carries retry_after_seconds, limit and the scope; the header carries Retry-After too.
    503rate_limit_unavailableA security class could not evaluate its limit at all and fails closed — retry shortly, do not keep hammering.

    Degraded is not normal

    When Redis is unreachable the limiter still enforces a per-process fallback, but it reports that path explicitly — X-RateLimit-Degraded: 1 on the response and a degraded state on the admin panel. A deployment that is quietly degraded should be repaired, not tolerated.

    An AI provider is unreachable

    Symptom. Rewritten posts arrive unmodified, or a rule with a rewrite configured stops sending.Cause. The provider is down, the key is wrong, or the rewrite was turned off for that task. A provider failure must never block delivery: the outcome is decided by the rule's fallback policy.

    AI fallback policy (per task)
    Fallback policyBehaviour when the provider fails
    SEND_ORIGINALDeliver the untransformed text. Delivery is never blocked by the provider.
    DROPDrop the post rather than deliver without the rewrite. The default policy.
    RETRYRequeue the job and try the provider again later.
    QUARANTINEHold the job for review instead of guessing.

    Delivery is never blocked by the provider

    A failed transform is counted and logged ([PIPELINE:AI_REWRITE:FAILED]) and the fallback policy decides what happens to the post. A rewrite that is disabled per task logs[PIPELINE:AI_REWRITE:OFF] and sends the original text — that is the intended path, not an error.

    Log history is empty or truncated

    Symptom. Old entries are gone, or history is thinner than expected. Cause.History is bounded on purpose. The logger keeps a bounded in-memory queue and, when it is full, evicts theoldest queued record (reported as dropped) so the newest context survives. Age-based retention then deletes rows past the policy age — seven days by default — while audit and security categories are excluded from deletion by policy.

    Shedding is not purging

    A dropped counter means bounded-queue eviction under load; it is not a deletion of stored history. Lowering a log level to reduce noise is also not a purge. If stored rows really are missing, check the retention policy before assuming corruption.

    A container is older than your .env

    Symptom. The bot reports it is unconfigured although .env is filled, or the validator warns container-env. Cause. Environment variables are read when a container is created, so a container started before the last .env change keeps the old values.

    Collect evidence before you ask for help

    A bug report is only actionable with the correlation id, the log slice and a machine-readable doctor report. Gather all three; they answer most follow-up questions before they are asked.

    Secrets are redacted for you

    Field-aware redaction runs on the logger and in error paths, so a doctor report or a log export is safe to attach. Verify anything you copy by hand is a line number or an id, not a token.
