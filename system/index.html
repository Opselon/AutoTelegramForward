    Shape of the system

    Nine subsystems, one deployable stack. The split is not decoration: it is the reason a Telegram session can be replaced without touching the REST contract, and the reason a log flood cannot slow a delivery down. Three languages carry the runtime — Python for the engine, Go for the control plane, Rust for the gateway — with Dart for the client and TypeScript for the dashboard.

    Runtime topology

    Import links only exist inside one language. What connects the languages is the wire: gRPC between the control plane and the engine, HTTP between the gateway and the API, MTProto between the engine and Telegram, and SQL to the two separate stores. Those 23 links are what this map draws — hover a component to trace them, click one for its files and evidence.

    Pipeline & rule engine· Service

    Policy resolution, cleaning, shortcodes, replacements, AI pass

    Python · domain model · 22 source files · 9,352 lines

    3 gRPC boundaries

    Control plane → engine, control plane → log store, engine → log store. All three are protobuf, all three fail loudly.

    5 HTTP boundaries

    Dashboard → gateway → API, mobile → API, CLI → running stack. The browser never sees an API key.

    4 SQL boundaries

    Engine database and log database are separate files, so history cannot lock the delivery path.

    How this map is verified

    A map that describes a system is only useful if it is allowed to say "I could not confirm that". The sweep that builds this page does three kinds of check, and publishes the failures in the same place as the successes.

    Derived, never typed

    Counts, node lists, protocols, ports and log tags are parsed fromscripts/sync-architecture.mjs reading this checkout at 22cb3f8. A number on these pages that is not in architecture.json does not exist.

    Every claim has a source

    12 inter-service links were emitted only after a real search hit in the repository — the matching files are printed with each link. No probe failed in this build.

    5 checked absences

    The strongest statements are the negative ones. Each of these is a search that came back empty on this checkout: Mobile speaks no gRPC · No secrets in the browser bundle · No label chosen by a language branch · Two separate databases · The engine opens no HTTP port.

    empty result Mobile speaks no gRPC — The mobile client never dials the engine directly: every call goes through the REST control plane. (searched: mobile/lib)

    empty result No secrets in the browser bundle — Neither the API key, the master key nor the AI provider address is shipped to the browser. (searched: web/frontend/src)

    empty result No label chosen by a language branch — A localised label is never picked by a hardcoded ternary — the catalogue lookup does it, and it falls back to English. (The language switcher itself still shows the target language natively, which is the point of a switcher.) (searched: core/infrastructure/telegram , core/application , atfcli)

    empty result Two separate databases — The logger never opens the engine database — the log store is its own file. (searched: logger , rust/logger/src)

    empty result The engine opens no HTTP port — The engine is reachable only over gRPC; there is no HTTP server inside the core. (searched: core)

    open item No committed credential defaults — Every credential in the compose file is an interpolation; no working secret is committed as a default. (hits: docker-compose.isolated.yml)

    The negative checks and the dropped probes are regenerated on every build, so a claim that stops being true stops being printed — the page cannot silently drift from the software it maps.
