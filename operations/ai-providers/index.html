    AI providers, keys and prompts in depth

    The layer under the rewrite toggle: config routes, the provider catalog, check-key, the endpoint guard, prompt versioning, the circuit breaker and outages.

    The AI rewriting feature page covers what a reader needs to switch the pass on: the per-task toggle, the configuration fields, the presets. This page is the layer underneath — the exact REST surface, what a key probe proves, which endpoints the core refuses to call, how versions are stored, what the resilience machinery does when a provider is slow or gone, and what the log says afterwards. Every statement here was read out of the files named in the section that makes it.

    Overview

    An AI rewrite is not a service you run; it is a stage inside the forwarding pipeline that a task opts into. The stage answers four questions and nothing else: should this task rewrite, with which prompt and which provider, did the answer survive validation, and what happens to the message when it did not. Everything below is one of those four answers.

    The configuration surface

    Eleven routes, all bearer-authenticated, all scoped to the verified tenant, all on /api/. The prompt routes deliberately are not under the /api/v1/ prefix: that prefix bypasses the bearer middleware, and the ownership guard would then have no identity to compare against.

    Registered in api/main.go; handlers in api/internal/handlers/handlers.go
    RouteWhat it returns or changes
    GET /api/ai-configsThe caller’s own configs, each one with its api_key already masked.
    POST /api/ai-configsCreates one. The core stamps owner_user_id from the verified identity, so a body cannot name another tenant, and fills what is left out (openai, gpt-4o-mini, user template {text}, temperature 0.7, enabled, en).
    PUT /api/ai-configs/{id}Update of a config you own. The core merges field by field: a non-empty model, base_url, system_prompt, user_prompt_template or target_language replaces the stored value, a blank or ***-masked api_key keeps the stored key, and a zero temperature keeps the stored one. Two sharp edges come with that: is_enabled is written exactly as sent, so a partial body that omits it turns the config off, and name and provider are not part of the merge at all.
    DELETE /api/ai-configs/{id}Removes it — deleted, or not_found when the id is not yours.
    GET /api/ai-configs/providersThe catalogue: id, label, default_base_url and a curated models list per entry. Both the dashboard and the mobile app render this call, so neither keeps a provider table of its own.
    POST /api/ai-configs/check-keyProbes an endpoint and key before anything is stored: success (the probe ran), healthy (it was accepted), latency_ms, a redacted detail, an error_code.

    POST /api/prompts/testRuns a real transform and sends nothing: prompt_id, ai_config_id and sample_text are required, version optional. The config must be yours, and a version you name is the one that runs.

    One handler exists that no route reaches

    A Go handler for testing a single config in isolation (TestAIRewrite) exists, and the core implements the RPC — but no route is registered for it in this checkout, so it is not reachable over HTTP. The wired-in test path is POST /api/prompts/test, which takes a prompt and a config together and runs the real transform without sending anything.

    Providers and model families

    The provider list is a registry, not a switch statement: an adapter is registered under a name and the rewrite path resolves the name out of the same registry, so anything you can pick is something that can be called. Twelve vendor entries exist under thirteen keys, because 9Router is registered both as 9router (the enum spelling) and ninerouter (the alias).

    • Most vendors speak one protocol. OpenAI, Groq, DeepSeek, OpenRouter, 9Router, xAI, Mistral, Together, Fireworks and custom all go through a single OpenAI-compatible adapter; Anthropic and Gemini have request shapes of their own. A custom config with nobase_url is refused outright — there is nothing to call.
    • An empty base_url means "the vendor's own endpoint". The adapter falls back to a per-provider default and appends /v1 when the URL you stored carries no version suffix. OpenRouter additionally gets the attribution headers this project sets.
    • The model list is curated, not enforced. It is what the pickers render;model is a free string on the wire, so a model released after this build can be typed into a config without a code change.

    Key handling

    The key is the one field with special rules, and they matter before an operator swaps one: it iswrite-only. The protobuf says so, the API never echoes it, and the core masks it on the way out.

    api/internal/handlers/handlers.go, the core servicer and core/infrastructure/security/crypto.py
    PropertyBehaviour
    At restStored in ai_configs.api_key_encrypted, encrypted by the core’s crypto service (AES-256-GCM with a random 12-byte nonce).
    On every readMasked as *** plus the last four characters of the stored key. The value in a GET answer is not a credential you can use, and not the value the operator typed.
    On updateAn api_key beginning with *** means "unchanged", and the stored key is kept — that is what lets a dashboard re-save a config it can only see masked.
    On probeThe same convention: a blank or masked key means "use the one already stored for that config id".
    In a refusalA provider message comes back with the key redacted out of it, and the detail is capped at 300 characters — enough to explain a refusal, never the secret.
    In the response shapeThe five check-key fields are always present, including a false for success: the answer is projected field by field rather than marshalled from the protobuf, so a client never has to read a missing field as a refusal.

    A masked value is evidence, not a value

    Because reads return ***9f2c, a client can prove which key is stored without holding it. Sending that value anywhere except an update or a probe sends a non-credential — treat ***… as a fingerprint.

    check-key, the pre-save probe

    A broken key that has been stored is worse than one that was refused: the config looks healthy in the panel and every message pays for it. POST /api/ai-configs/check-key is the gate in front of that. It is deliberately not a rewrite — it asks for the cheapest call the provider offers.

    1. 1

      Ownership first

      A named ai_config_id must belong to the caller, because the probe would spend that config’s credentials. A foreign or unknown id answers config_not_found — as a refusal, not an error.

    2. 2

      Blanks are filled from the stored config

      Whatever the caller leaves out is taken from the config it named, so a UI can re-check a saved key without ever receiving it. A masked key counts as "leave it as stored".

    3. 3

      The request is assembled per provider

      One token, temperature 0: OpenAI-compatible providers call /chat/completions, Anthropic calls /messages, Gemini calls :generateContent. The probe budget is 12 seconds and redirects are not followed.

      POST <base>/chat/completions   {"model": "…", "max_tokens": 1, "messages": [{"role":"user","content":"ping"}]}
    4. 4

      The endpoint guard runs before any socket is opened

      The URL the tenant typed is a request the core makes from inside your network, so it is checked first — with the name resolved, not merely parsed.

    5. 5

      The answer is classified, then redacted

      A 2xx means the credentials work. 401/403 is invalid_key, 404 endpoint_not_found, 429 rate_limited, 5xx provider_error. One quirk is handled: a 400 that mentions max_tokens is retried once with max_completion_tokens, so a newer model is not reported as a broken key.

    The probe reports a status class, never a provider body verbatim
    error_codeWhat it means
    missing_provider / unknown_providerNo provider named, or the name is not in the registry. Nothing was sent anywhere.
    missing_key / missing_endpointThe probe would have nothing to authenticate with, or no URL to call.
    config_not_foundThe ai_config_id you named is not yours. A refusal, not a leak.
    endpoint_invalid / endpoint_blockedThe URL is not plain http(s), or the guard refused the host — see the guard table below.
    endpoint_unreachableThe connection failed, or the name did not resolve. Only the exception’s type name is reported: a connection message can carry an internal host.
    timeoutNo answer inside the probe budget (12s). The provider is not necessarily wrong — it is slow.
    invalid_keyThe provider answered 401 or 403. Its own message is passed through with the key redacted out of it.
    endpoint_not_found / rate_limitedThe provider answered 404 (wrong path or model) or 429.
    provider_error / probe_rejectedThe provider answered 5xx (only the status is reported) or some other status.

    Read two fields, not one

    success means "the probe ran and reached an answer"; healthy means "the endpoint accepted these credentials". A guard refusal reports success=false precisely so it is never mistaken for a provider outage — nothing left the process.

    The endpoint guard

    A tenant-supplied URL is a server-side request. Left unchecked it is a port scanner with a status code in the reply, aimed at whatever network the core happens to live in. The guard exists for that, and it runs twice: at the probe (with DNS resolution) and again at every write, because a stored endpoint is replayed on every rewrite afterwards.

    • Private model servers are opt-in. SetATF_ALLOW_PRIVATE_AI_ENDPOINTS to 1, true, yes oron on the core and a LAN address becomes callable. Every other row of the table still applies, so the switch widens one class of address and nothing more.
    • One bad answer is enough. When the guard resolves a name it inspects every address it resolves to — a hostname answering with both a public and a private address is refused, not sampled.
    • Know what the write-time check does not do. The probe resolves names; the create and update path calls the same guard without a resolver, so it is a syntax, hostname and literal-address check. A name that resolves into private space is therefore refused at probe time, while a literal private address is refused at both. A refused write surfaces as gRPCINVALID_ARGUMENT carrying the guard code, so the API answers 400 with something a client can translate instead of a generic server error.
    • The redirect is not followed. A provider that answers with a redirect is classified on the redirect itself, so a probed name cannot hand the request to a second host the guard never saw.

    Rollback is implemented but not routed

    The prompt service can roll a template back: it copies the target version's text forward as a new version with the summary "Rolled back to vN", which keeps the history linear instead of rewriting it. No route, RPC or CLI verb calls it in this checkout, and no route lists version history either — GET /api/promptsreturns the current version number. To roll back from a client, read the text you want and PUT it with the version you got; to see the whole history, read the store directly.

    What runs per message

    The order matters more than the individual steps, because two of them are decisions about the same text. This is the sequence for one message on a task with a rewrite attached.

    1. 1

      Content policy transforms first

      Per-task content rules rewrite the text before the model is asked, so the model never sees text the task was already going to strip and a rewrite cannot resurrect content a rule removed.

    2. 2

      The gate answers one question

      A task rewrites when it has an ai_config_id and its ai_rewrite_active property is true — which it is unless the task metadata carries paid_addons.ai_rewrite and that value is false. When the gate is shut, the pipeline logs the off-path line and forwards the text unmodified; it does not treat the task as broken.

      [PIPELINE:AI_REWRITE:OFF] [7f3a91c2] Rule 3f1c9a2e keeps cfg=9a11c7f0 but rewrite is disabled (smart_ai_rewrite=False, paid_addons=False) — delivering unmodified text
    3. 3

      The prompt is resolved

      The task’s prompt id, and an optional pinned version, is rendered by the prompt service; without a prompt id the AI config’s own system_prompt is used, and an empty one falls back to a plain instruction to rewrite cleanly. A prompt id that cannot be resolved is logged and the request continues with the config’s prompt rather than failing the message.

    4. 4

      The request is shaped for the message type

      A message with media is treated as a caption: a 1024-character budget instead of 4096. The timeout comes from the task (ai_timeout_seconds, default 15, clamped between 1 and 120), and the target language is passed as auto.

    5. 5

      The transform runs under a deadline

      The call is wrapped in a timeout, goes through the circuit breaker, and its answer is validated before anything is sent. A validated answer replaces the text; anything else hands over to the fallback policy.

    6. 6

      The tail of the pipeline still runs

      Final replacements, then header and footer, then the advanced content transforms — and the transformed text is capped again at delivery. A rewrite cannot smuggle text past the header/footer stage or past the cap.

    Two per-task AI settings the rewrite path does not read

    The settings registry declares ai_creativity (default 0.7) andai_max_tokens (default 600), and the task editors render them. No code in the rewrite path reads either: the request sends the temperature of the AI config, and the output cap is the validator's caption/text limit. Set creativity on the config, not on the task.

    • Retries happen below the breaker, not through it. One attempt gets 45 seconds of network budget, and a transient status (408, 425, 429, 500, 502, 503, 504) or a timeout is retried twice inside the same call the breaker is timing.
    • A configuration trips, not a vendor. The registry hands out one breaker per id it is given. Two configs pointed at the same vendor keep independent state, and the breaker that records an outcome is the one belonging to the config actually used.
    • Read the signature, not the intent.record_failure(is_transient=…) accepts whether a failure was transient, and the callers answer honestly — but the state machine increments the failure counter either way and does not consult the flag. A non-transient 401 counts toward the same threshold of 3 as a timeout.
    • Recovery is lazy and free. Nothing schedules a timer: the state is re-evaluated when someone asks, so an open circuit costs nothing while idle and the first rewrite after the window is the probe that decides whether to close it again.

    When the provider is down

    A failed transform is a per-task decision, not a global setting, and the shipped default is the strict one. The task field is ai_fallback_policy.

    The default fails closed, and that is worth knowing before an outage

    With no policy set, a task uses DROP: the message is not delivered. OnlySEND_ORIGINAL forwards the untransformed text. Two further consequences of reading the code rather than the intent: RETRY and QUARANTINE both return "no text" from the transform stage, so in this checkout neither delivers the message, and no code in the forwarding path reads theai_retry: / ai_quarantine: stage reasons — there is no requeue and no quarantine store to find them later. If a rewrite is a nice-to-have, say SEND_ORIGINAL explicitly.

    The drop happens early, too: the transform stage runs before a delivery job is enqueued, so a message dropped by the fallback policy never becomes a queue entry — the retry budget and the dead-letter list never see it. The evidence is the log line and the recorded transform stage, and that is all.

    Where this stands

    The project keeps its own status list in docs/feature_catalog.json: 18 entries generated from a source inspection, each carrying an implementation_status (14 implemented, 2 partial, 2 planned). AI rewriting is not one of them — no entry in that catalogue covers it, so this page claims no catalogue status for it.

    What it claims instead is narrower and checkable: the behaviour described here is implemented in the files named in each section. Where something is absent — the unrouted test handler, the unrouted rollback service, the missing version-history route, the per-task AI settings the rewrite path never reads — it is called out as absent rather than rounded up. Treat this as documented-in-code behaviour, and the catalogue as the list of features the project formally tracks.

    Worked examples

    Three sequences: prove and store a credential, attach it to a task with the policy you want, then own a prompt template through a test and an edit.

    The interfaces are the other way in

    Everything the REST surface does is reachable from the shipped clients: the Telegram bot has an AI menu that lists configs and starts the add flow, the dashboard renders the provider catalogue and the prompt templates, and the mobile app calls the same check-key route before saving. The differences are convenience, not capability, and the clients share one server-side catalogue so they cannot drift apart.
