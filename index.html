    How it works

    One message, five stages, no silent failures

    Ingest, gate, transform, queue, deliver. Each stage is inspectable from the CLI and the dashboard, and each one has a defined answer for failure instead of hope.

    1. 1

      Ingest

      A session polls every source chat of every enabled task. Albums are aggregated into a single job and the channel cursor is committed atomically, so the poller cannot race the connection or replay a batch.

    2. 2

      Gate

      The policy engine decides cheapest-first: length gates, media allow/deny, Unicode-folded word-boundary blacklists and whitelists, then ReDoS-refused regex patterns. A SHA-256 fingerprint drops content already delivered.

    3. 3

      Transform

      The cleaner strips URLs, mentions, hashtags, phone numbers and emojis while UTF-16 entity offsets keep bold and italic spans intact. Literal and regex replacements run in one deterministic pass, then shortcodes render the header and footer, and the optional AI pass rewrites the body.

    4. 4

      Queue

      The delivery is persisted as a job and picked up by a lease-based worker with exponential backoff and jitter. Ordered lanes keep a burst in posted order; a failing job retries, then lands in the dead-letter queue where it can be inspected and replayed.

    5. 5

      Deliver

      Copy mode posts the content as your own message, direct forward keeps the native quote header, and the branding hop posts through an intermediate channel before the target. Edit and delete events follow the message; a Telegram timeout is recorded as OUTCOME_UNCONFIRMED rather than guessed at.

    Every state a delivery passes through is recorded: RECEIVED · VALIDATING · AUTHORIZED · ACCEPTED · IN_PROGRESS · RETRY_WAIT · SUCCEEDED · FAILED · CANCELLED · OUTCOME_UNCONFIRMED.

    Security

    Isolation you can hand to a customer

    Multi-tenant from the database up, with the failure mode chosen deliberately: an unproven scope denies instead of widening.

    Fail-closed tenancy

    Every read and write is scoped to the authenticated numeric Telegram user id across bot, dashboard, mobile, REST and gRPC. An unproven scope denies instead of widening.

    Encrypted at rest

    AES-256-GCM for sessions, bot tokens, AI keys and backup bundles. Secrets are field-aware redacted in log lines and error traces.

    Private internals

    Core and logger bind to internal interfaces only, and the internal gRPC surface requires a shared credential — it is not a public port.

    Single-use login links

    A dashboard link carries a random, hashed code with a ten-minute TTL that is burned on first use — never a session token — so a link that outlives its click is worthless.

    Answers

    Questions people actually ask

    What exactly is AutoTelegramForward?

    A self-hosted Telegram message routing platform. A task watches one or more source chats and delivers to one or more targets, applying per-task content rules, templates and an optional AI rewriting pass on the way. It ships as four microservices you run yourself.

    Can one task read several channels and post to several destinations?

    Yes. Sources and targets are lists, so a single task can route many channels into many destinations. The primary source and target are derived from the lists and always kept consistent.

    How do I link my Telegram account to the dashboard?

    Ask the bot for the dashboard. It mints a single-use login code, the link opens the dashboard once, and the code is burned on first use with a ten-minute TTL. No password is created and no Telegram id is ever accepted in the exchange.

    Do I need an AI provider to use it?

    No. AI rewriting is an optional per-task toggle. Without it the cleaner, filters and templates still work exactly the same, and a provider that is down never blocks delivery.

    How do I install it?

    Clone the repository and run ./scripts/setup.sh on Linux or macOS, python scripts\bootstrap.py on Windows, or the zero-prerequisite installers. Each path ends in the same guided wizard that builds the stack and proves every service is serving.

    Is it multi-tenant?

    Yes, and isolation is fail-closed: every read and write is scoped to the authenticated numeric Telegram user id, across the bot, dashboard, mobile app, REST API and gRPC services.

    How do I know which features are actually finished?

    The status board is generated from the repository's own feature catalog on every build: 14 implemented, 2 partial and 2 planned. Nothing is presented as done unless the catalog says so.

    Which Telegram content types are supported?

    Text, photos, albums, video, documents, audio, voice notes, video notes, stickers, polls, locations, contacts and copy-protected content that is re-uploaded rather than forwarded.
