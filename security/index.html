    Security

    Security & tenant isolation

    How the platform keeps tenants apart: fail-closed identity scoping across bot, dashboard, mobile, REST and gRPC, AES-256-GCM at rest — and its stated limits.

    On this page
    • Isolation model
    • Where it is enforced
    • Cryptography
    • Secrets handling
    • Network posture
    • Audit trail
    • Known limits

    AutoTelegramForward runs one installation for one operator's accounts — and optionally for many. The design decision that shapes everything else is that isolation is fail-closed: the default answer to "may this caller read this row?" is no, and a caller who has not linked a Telegram account can read nothing at all.

    Isolation model

    Identity is a number, not a claim. Each surface resolves the caller to a numeric Telegram user id, that id travels with the request through every layer, and each data access is scoped by it.

    Telegram bot

    Commands resolve the caller to a numeric user id and load only that account's tasks, sessions and history.

    Web dashboard

    Bearer token from the authentication routes; every request carries the resolved identity into the handler.

    Mobile app

    Signs in through the same routes and talks to the same API — there is no second, weaker path.

    REST API

    Tenant-scoped handlers; an unlinked account resolves to id 0 and therefore owns nothing.

    gRPC services

    Internal calls carry the caller identity that the control plane verified, never one the client asserts.

    Administration

    Mounted behind RequireAdmin: without admin rights the route set is unreachable, not merely hidden.

    Tested, not asserted

    Tenant isolation has dedicated Go test files in the API package and Python tests in the core. That is why the front page can claim zero cross-tenant leaks without an asterisk.

    Secrets handling

    • The API never echoes a secret. The environment-contract route reports set: true/false per key plus a fix hint — never the value.
    • Validation scans for committed secrets as part of the read-only check set, alongside layout, compose, catalog parity and ports.
    • Backups can be exported without secrets, so a configuration bundle can be shared for review while credentials stay home.
    • Setup writes .env with restrictive permissions and refuses to continue when a required key is missing or malformed.

    Audit trail

    The access logger mirrors every request — successes included, not just failures — into the central logger with the verified actor, the subject task and the correlation id. That is what makes "who changed this rule, and what did it do next" answerable after the fact.

    Attributable entries

    Each entry names the actor, the service, the level and the subject.

    Bounded queries

    Filter by service, level, text and time; results page instead of flooding.

    Exportable evidence

    History exports as JSON or CSV, and purge is an explicit, scoped action.

    Known limits

    Being straight about the boundaries is part of the design. These are the things you should know before you rely on the platform in a regulated setting.

    • Static analysis reports pre-existing findings in the backup export helper. They are known, tracked and do not grant a tenant access to another tenant's data — but the export path deserves your own review before you handle third-party data.
    • TLS is expected at your reverse proxy. The service itself speaks plain HTTP on the internal network by design.
    • Encryption keys are your responsibility: lose the key material and encrypted backups cannot be recovered, by us or by anyone.
    • Your Telegram accounts remain subject to Telegram's own rate limits and terms; the platform is built to respect FloodWait rather than defeat it.
