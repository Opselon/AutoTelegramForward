    Authentication

    API authentication

    Authenticating against the control plane: the bearer JWT, which routes stay public, the rate-limit classes, correlation ids and the gRPC credential.

    On this page

    Overview

    The Python core owns identity: it issues the seven-day session token and answers "is this token valid, and for whom?". The Go control plane owns enforcement: it presents the token to the core on every request and scopes the call to the identity that comes back. There is no path where a client asserts who it is.

    102 routes parsed from api/main.go68 require a token7 on the public auth mux

    One consequence is worth stating early, because it explains most of the behaviour on this page: the token is atenant key, not a role. Everything tenant-scoped is filtered by the verified user id server-side, and an ownership failure looks exactly like a missing row.

    Obtaining a token

    Two routes mint a session, and neither of them is a user id you can post. The bot link is the usual one; the password and Mini App paths exist alongside it for clients that have their own proof.

    The three ways to obtain a 7-day session (all of them end at the same JWT)
    RouteCredential it takesWhat it gives back
    GET /api/auth/bot-login-linkAuthorization: Bearer <expiring session>Mints the caller's own single-use code and answers {code, expires_at, link}. This is the re-authentication path: a client whose stored session is dead asks the bot side for one fresh link instead of looping the user through a login form.
    POST /api/auth/exchange-bot-token{login_code}Trades that code for the 7-day session. The body carries no user id — a Telegram id is public, so the code is the only thing that names the account.
    POST /api/auth/login{username, password}The username/password path for accounts that registered without Telegram (or alongside it). A password login never creates or moves a Telegram binding.
    POST /api/auth/tma{init_data}The Telegram Mini App path. The signed initData is verified (HMAC-SHA256 over the sorted data-check-string, duplicate and stale auth_date refused) before a token is issued for the numeric user id inside it.

    Read the session, do not decode it

    A JWT payload is readable by anyone holding the token, so it is not a place to keep a secret — but decoding it is still not verification. Clients are expected to prove the token against the API (below) rather than trust the claims they can read out of it.

    Sending the token

    One header, on every authenticated request. The middleware validates it before the handler runs, and the handler only ever sees the verified identity — never a header or body field that claims one.

    • A shared key can replace it for machines. When the operator setsATF_API_KEY, any request that does not carry a bearer credential must present the same value inX-API-Key; anything else is 401 {"error":"unauthorized"}. The health routes,/api/version, /api/openapi.yaml and the whole /api/auth/ surface are exempt, and a bearer request is passed straight to the JWT path — the key is a machine gate, not a second factor.
    • Store it once, treat it like a password. The shipped clients keep the session in one place, check the token's own expiry before rendering, and prove it against the API on load, so a revoked session produces one login prompt instead of a page that dies mid-render.
    • GET /api/auth/me is the cheap probe. It is the intended way to answer "is this token still a session?": it returns the verified identity or a refusal. A client that stores a token should call it on mount and treat a refusal as one session transition, not as a per-request retry loop.
    • The token is a credential, not a preference. It identifies a tenant, so anything that holds it — a browser, a phone, a CLI — should hold it the way it would hold a password: no logging, no URLs that end up in chat history, no copies left in build artefacts.

    Public vs authenticated

    The muxes are the contract. /api/auth/ is mounted without a bearer wrapper (each of its handlers decides for itself), the service-health and system routes are public, and everything else under /api/ is wrapped in RequireAuth. The administration plane adds a second gate,RequireAdmin, on top of it.

    The generated route table marks the auth mux as unauthenticated

    The build-time scan of api/main.go sees /api/auth/* mounted outside the bearer wrapper, so it lists every route there — including GET /api/auth/bot-login-link — as public. That is true of the mux and false of the handler: the handler refuses a request without a valid bearer token. Treat the table as a map of the muxes, and this page as the authority on which routes need a credential.

    Rate limits

    The limiter is a Redis-backed token bucket with a circuit breaker, keyed on the verified identity — never on a client-supplied field — so ?user_id=, X-User-Id or a body field cannot move a caller into another tenant's budget. Requests that have not been authenticated yet are keyed on the peer address, and only a proxy the operator declared trusted may move that address.

    Correlation ids

    Every request ends up with one correlation id, whether the caller supplied one or not. It is echoed on the response, attached to the outgoing gRPC metadata, and recorded in the access trail, so an API call and the delivery it caused can be joined without guessing at timestamps.

    One documented header has no implementation

    The shipped docs/openapi.yaml describes an optional signed-session binding via X-Session-Id. No code in the repository reads that header — the bearer middleware is the only credential check — so do not build a client against it. The document is descriptive prose there, not a contract the binary enforces.

    Error model

    Refusals are JSON with an error string a human can read and, where the failure has a machine meaning, a code a client can translate. Two families exist and they are not interchangeable: handlers answererror_code (and the core's own refusal token is passed through verbatim), while the rate limiter answerscode. Some early refusals — a missing bearer header, an unparseable body, a gRPC failure mapped bygrpcError — carry only error, so a client should treat the code as optional and the status line as authoritative.

    Internal gRPC credential

    The control plane talks to the Python core over gRPC, and every servicer there takes the acting tenant from a request field (owner_user_id) — which the API stamps from the identity it verified. That contract alone could not tell the API from any other process that can open a socket to the core, so the surface can additionally require a shared credential.

    • One variable, both sides. ATF_CORE_RPC_TOKEN is read by the core's server interceptor and by the Go client, which attaches authorization: Bearer <token> to every unary and streaming call. A deployment cannot enable it on one side by accident: a mismatch fails every RPC loudly at deploy time.
    • Unset is the old behaviour, said out loud. With no token configured the interceptor is not installed and the core logs a warning explaining that anything on the network can act as any tenant. Nothing is silently assumed to be fine.
    • Refusals keep their shape. A missing, malformed or wrong credential isUNAUTHENTICATED before the servicer runs; the comparison is constant-time, the value is never logged, and the refusal preserves the method's cardinality so a streaming call does not turn into an internal error.
    • The logger is a separate trust domain. It is dialled without the credential on purpose: the secret authenticates this API to the core, and the logger does not need it.
