    286 modules, 878 resolved imports, 9 subsystems and 3 import cycles — counted from this checkout, not from memory. Every node on the map links back to its file on GitHub, so a claim about coupling here can be checked in one click.

    How to read the map

    One node = one unit of dependency

    Python, Dart, Rust and TypeScript nodes are files; Go nodes are packages (a Go file is never a unit of dependency on its own). The legend on the canvas says which is which, per language.

    One edge = one resolved import

    Edges come from parsing import/from … import, Go import blocks, use/mod statements and relative ES imports, then resolving each specifier against the file index. Anything that resolves outside the repository (a third-party package) is intentionally not drawn.

    Size = lines, colour = subsystem

    A node grows with the square root of its line count, so a 3,000-line service does not swallow the canvas. Node size is a scale, not a score: coupling is what fan-in and fan-out measure.

    Note

    What the ranking actually shows: core/domain/entities.py leads with 51 dependents and core/domain/value_objects.py follows with 37, which is what a layered core is supposed to look like — the domain model is the thing everything else may depend on. Persistence appears high as well (25 dependents on the repository layer): that coupling is deliberate here, because reaching storage any other way would bypass the sanctioned write path. The site's own utils/paths.ts ranks second — every page depends on the base-path helper, so it is this website's domain module.
