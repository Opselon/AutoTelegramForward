    Task lifecycle

    Durable task lifecycle

    How long-running work survives a restart: the six states, the allowed transitions, idempotent submission, retry backoff, refusal codes and the 64 KiB bounds.

    On this page
    • Why a task queue
    • States and transitions
    • Task kinds
    • Idempotent submission
    • Attempts and backoff
    • Bounds and refusals
    • Walkthrough

    A session backup, a dead-letter replay, a whole-installation export: each of these outlives the HTTP request that starts it. Rather than holding a connection open, the API writes a row and returns it. The row is the contract — poll it, cancel it, retry it — and it is owned by the same tenant rule as everything else, which is why a foreign task id answers exactly like one that does not exist.

    The 201/200 answer is the whole handshake

    POST /api/tasks returns the stored row, so a client does not have to follow up just to learn the id. The id, the state and the attempt budget all come back in the same response that accepted the work.

    Why a task queue instead of a long request

    • ·Restarts do not lose work. The row is in the database, so a container replaced mid-backup comes back to a claimable PENDING job rather than an orphaned promise.
    • ·Progress is observable. GET /api/tasks shows the state, the attempt count and the last error, so "is it still running?" is a query, not a guess.
    • ·Failures are recoverable. A transient Telegram or network failure reaches RETRY_WAIT with backoff; a spent budget reaches FAILED, where an operator can retry it deliberately.
    • ·Retries are safe. The idempotency rule means a client that retries a submission gets the original job back, not a second copy of the work.

    States and transitions

    1. 01

      PENDING

      Accepted and stored. Any worker may claim it; nothing has run yet.

      cancellable

    2. 02

      RUNNING

      A worker holds the claim and is executing. The attempt counter has already been incremented.

      running_not_cancellable

    3. 03

      RETRY_WAIT

      The attempt failed in a way that is worth retrying. The backoff delay is counted down, and the job stays cancellable while it waits.

      cancellable

    4. 04

      SUCCEEDED

      The work finished and its result is stored with the row. Terminal.

      not_cancellable

    5. 05

      FAILED

      The attempt budget is spent, or the failure was not worth retrying. Terminal — unless the owner explicitly retries it.

      retryable

    6. 06

      CANCELLED

      The owner stopped it before it ran, or while it waited for a retry. Terminal.

      not_cancellable

    RUNNING is honest, not optimistic

    A cancel request against a RUNNING job answers running_not_cancellable rather than pretending to stop it. The worker only moves to CANCELLED if it observes the request cooperatively; otherwise the job finishes and lands on SUCCEEDED or FAILED. Reporting CANCELLED for a job that is still running would be a lie that a later poll would contradict.

    An unknown kind is refused, not guessed

    The kind must be one of the four above. Anything else answers 400 unknown_task_kind — the queue dispatches on a closed set, so a typo cannot silently queue work that nothing will ever run.

    Idempotent submission

    The identity of a job is the trio of owner, kind and idempotency_key. The owner comes from the verified token — never from the body — so two tenants may use the same key without colliding, and a client that retried a submission after a timeout gets its original job back instead of duplicating the work.

    Choose a key that describes the work, not the attempt

    A key derived from the intent — the day, the batch, the rule — makes a retry safe. A random key makes every retry a new job, which is exactly the behaviour idempotency keys exist to prevent.

    Retry behaviour, in the order you will meet it
    RuleValueWhy
    Default attempt budget3 attemptsEnough to ride out a transient failure, short enough that a permanent one is reported the same day.
