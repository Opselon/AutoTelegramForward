## Audit findings (evidence-driven, verified against live DB + code)

### P0 — Real cross-tenant data exposure
1. `api_credentials` has NO `owner_user_id` column. `list_all()` / `get_default()`
   return any tenant's `api_hash_encrypted`. Backup export ships global credentials
   to any non-admin tenant (confirmed: servicers.py:922 → create_snapshot →
   `self._creds.list_all()` unscoped).
2. Prompt templates have NO owner scoping. `ListPromptTemplates` /
   Create/Update/Delete accept any id — tenant A can read/modify tenant B's prompts.
3. DLQ + delivery stats are unsoped: `ReplayDeadLetter`, `PurgeDeadLetter`,
   `ListDeadLetter`, `GetDeliveryStats` ignore caller identity — tenant A can
   replay/purge tenant B's dead-letter jobs and see all rules' live stats.

### P1 — Observability gaps
4. No ERROR/WARNING rate-limit / flood-wait structured events with retry counts.
5. Log events lack a stable `event_code` field (only free-text category).

## v12.1 — bot-layer tenant isolation (2026-10-11, PR #17 merged 8725be2)
Root cause: the bot resolves entities by callback id (`aid:<uuid>`, `rrm:<uuid>`,
`cred_default:<uuid>`), so the v12 HTTP/gRPC guards did not cover it — a
non-admin could forge a callback payload and read/mutate/delete another
tenant's rules, filters, AI configs, credentials, sessions, and execute
health checks / rewrites billed to another tenant's API key.

Use-case layer (one enforcement point per entity, `owner_user_id=None` keeps
the legacy/admin scope):
- SessionUseCases.get_owned/delete_owned
- ForwardRuleUseCases.get_owned/update_owned/delete_owned/toggle_owned
- FilterRuleUseCases.get_owned/delete_owned
- AIConfigUseCases.get_owned/update_owned/delete_owned + health_check_owned +
  test_rewrite_owned (guard the provider boundary)
- ApiCredentialUseCases.get_owned/list_by_owner/set_default_owned/delete_owned

Bot layer: ProBotUI._scope_uid() (admin -> None, else Telegram id; empty
admin_ids keeps the single-tenant behaviour exactly). 11 forged-id AI reads,
toggle + 3 edit steps, rule delete/toggle/del-confirm, credential
set_default, remaining list_all reads, FSM session pickers,
_finish_rule_creation, _fetch_dialogs(owner) all routed through the guards.
AI configs + filter rules created from the bot now stamp owner_user_id.

Evidence: 335 pytest pass (was 332), 20 adversarial isolation tests, Go
build/vet + tsc clean, PR #17 CI all green (python/go/docker), squash-merged.
Live: owner sees 2 rules / 1 AI config, tenant B sees 0; B spoofing A's
owner_user_id in backup export gets only B's own rows (0 rules/creds/sessions).
Capacity: 200 tenants x 5 rules seeded 148 ms, scoped read 0.33 ms/owner,
200/200 adversarial get_owned probes blocked.
