    Connection map (3D)

    Imports tell you how one language is arranged. Connections tell you how the system behaves: 23 links across 16 components, every one of them derived from a real call site in the checkout. Orbit the map, then replay one of the 3 traced paths and watch a packet cross the same boundaries a live message crosses.

    From an incoming Telegram update to a delivered copy in every target chat, with the durable queue absorbing rate limits.

      MTProto push from the source chat the session is authorised for.

      PIPELINE:INGESTPIPELINE:DIALOG_FETCH
    2. 2

      Normalise @ core-ingest

      Album items are aggregated and the update is turned into a domain event.

    3. 3

      Resolve policy @ core-pipeline

      Matching tasks, per-source/policy overrides, whitelists and blacklists.

      PIPELINE:POLICYPIPELINE:POLICY_TARGETPIPELINE:NO_RULESPIPELINE:NO_MATCH
    4. 4

      Filter & rewrite @ core-pipeline

      Filters, cleaner, shortcodes, replacements — and the optional AI pass.

      PIPELINE:FILTERPIPELINE:CLEANERPIPELINE:TRANSFORMPIPELINE:AI_REWRITE
    5. 5

      Rewrite (optional) @ ai-rewriter

      Only when the task enables it; an unreachable provider passes the text through.

      PIPELINE:AI_REWRITE
    6. 6

      Enqueue per target @ core-queue

      One durable job per target with an ordering key, so bursts keep their order.

      PIPELINE:ENQUEUE
    7. 7

      Lease & deliver @ core-queue

      Lease-based workers with exponential backoff and FloodWait-aware rescheduling.

      PIPELINE:RETRYPIPELINE:FLOODWAIT
    8. 8

      Delivered @ telegram-cloud

      Copy mode or native forward, into the target chat or forum topic.

      PIPELINE:DELIVERED
    9. 9

      Recorded @ logger-svc

      Every stage, drop and outcome lands in the log store with a correlation id.

      PIPELINE:DROPPIPELINE:FILTER_DROPPIPELINE:DUP_FILTERPIPELINE:DELIVERY_FAILPIPELINE:DELIVERY_TIMEOUT
    1. 1

      Operator saves @ web-ui

      A tenant-scoped token is attached to the request; no API key ever reaches the browser.

    2. 2

      Gateway proxies @ web-backend

      The Rust gateway forwards to the API and keeps upstream addressing server-side.

    3. 3

      Guardrails @ api-guardrails

      Correlation id, access log, log-policy gate and audit event are applied first.

    4. 4

      Authorise @ api-rest

      Fail-closed tenant check: the rule is only touched if it belongs to the caller.

    5. 5

      RPC @ core-grpc

      The write becomes a protobuf call on the engine surface.

    6. 6

      Apply @ core-pipeline

      Optimistic concurrency on the rule version; metadata[content_policy] carries the per-task rules.

    7. 7

      Persist @ core-storage

      Transactional write plus the outbox entry used for audit.

    8. 8

      Audit @ logger-svc

      Before/after images are written to the log store for attribution.

    1. 1

      Open the log explorer @ web-ui

    2. 2

      Stream @ web-backend

      SSE feed so the view updates without polling.

    3. 3

      Query @ api-rest

    4. 4

    Protocol boundaries

    12 boundaries, and the file that proves each one. A boundary is where a version mismatch, a timeout or a serialization change becomes visible — which is exactly why they are worth listing instead of hiding behind "microservices".

    api → core

    gRPC :50051

    Every rule, session and delivery command crosses this boundary as a protobuf RPC.

    verified in: api/internal/handlers/system.go, api/internal/handlers/system_test.go, api/main.go

    api → logger

    gRPC :50052

    The API writes its own logs, audits and latency events to the same central store.

    verified in: api/internal/handlers/system.go, api/internal/handlers/system_test.go, api/main.go

    core → logger

    gRPC :50052

    Pipeline stages emit [PIPELINE:*] events through the shared log client.

    verified in: core/application/pipeline.py, core/config.py, core/main.py

    core → AI rewriter

    HTTP OpenAI-compatible

    Optional rewrite pass. Unreachable provider degrades to pass-through, never to data loss.

    verified in: core/infrastructure/ai/providers.py

    Web gateway → api

    HTTP reverse proxy + SSE

    Server-side proxy keeps the API key out of the browser and streams the live log feed.

    verified in: web/backend/src/main.rs

    web-frontend → Web gateway

    fetch /api/v1/*

    The React app only ever talks to its own origin; the gateway owns upstream addressing.

    verified in: web/frontend/src/api.ts

    mobile → api

    HTTPS + bearer token

    Same REST contract as the dashboard, with offline-tolerant error surfaces.

    verified in: mobile/lib/core/api_client.dart, mobile/lib/core/app_state.dart, mobile/lib/core/env.dart

    DevOps CLI → api

    HTTP health + config probes

    Diagnostics read the same endpoints an operator would curl.

    verified in: atfcli/api.py, atfcli/cli.py, atfcli/commands/db.py

    root → Web gateway

    Caddy reverse proxy

    Optional --profile tls terminates TLS and forwards to the gateway.

    verified in: Caddyfile

    contracts → api

    protoc / buf

    The Go stubs and the Python servicers are both generated from one .proto file.

    verified in: api/proto/autoforward.pb.go, api/proto/autoforward_grpc.pb.go

    contracts → core

    protoc / buf

    One schema, two runtimes; a mismatch fails at the gRPC boundary, not in production.

    verified in: core/infrastructure/grpc_server/account_servicer.py, core/infrastructure/grpc_server/admin_servicer.py, core/infrastructure/grpc_server/servicers.py

    website → root

    build-time ingestion

    The site derives its numbers from the same files a contributor edits.

    verified in: website/scripts/sync-architecture.mjs

    Links that do not exist

    The topology is defined as much by what is missing. Each of the following is a search over the checkout that came back empty on this build — a negative claim the site re-checks rather than asserts once.

    Mobile speaks no gRPC

    The mobile client never dials the engine directly: every call goes through the REST control plane.

    searched: mobile/lib

    No secrets in the browser bundle

    Neither the API key, the master key nor the AI provider address is shipped to the browser.

    searched: web/frontend/src

    No label chosen by a language branch

    A localised label is never picked by a hardcoded ternary — the catalogue lookup does it, and it falls back to English. (The language switcher itself still shows the target language natively, which is the point of a switcher.)

    searched: core/infrastructure/telegram , core/application , atfcli

    Two separate databases

    The logger never opens the engine database — the log store is its own file.

    searched: logger

    The engine opens no HTTP port

    The engine is reachable only over gRPC; there is no HTTP server inside the core.

    searched: core

    Note

    These absences are what makes the isolation boundary believable: if nothing in the mobile client can reach the engine directly, then every access it makes has passed the REST control plane's tenant check.

    The links here are the runtime view. For the code-level view — which module imports which, and where the coupling is concentrated — open the dependency atlas, or go back to the atlas overview.
